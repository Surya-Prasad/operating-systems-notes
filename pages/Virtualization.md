		- Most of the instructions of the app directly run on the hardware

- ## Broad Classifications
	- ### Process VMs
		- eg: JVM
		- Java itself is a virtualized compiler
		- Guy Steele came up with Java and his goal with Java was to have a eternal programming language -> Runs anywhere
		- Java is compiled not to the machine binary, but to a Java Intermediary Bytecode -> Their own software ISA and that is the code that is distributed
		- To run the JIB, you need an interpreter for the bytecode and runs it
		- Java Application -> Intermediary Bytecode <- Java VM
		- The underlying system just emulates it
		- The problem though is that there is no isolation
			- JVM treats everything that is running as one process
			- It means that there is no protection and everything is shared

- ## Popek-Goldberg (1974)
	- The paper has a fundamental theorem
	- Proposes a 'sufficient condition' for a hardware to virtualize.
	- Theorem states that 'Sensitive instructions should be a subset of privileged instructions'
		- Sensitive Instructions:
			- Those that change the state of the machine or depend on the state of the machine
			- As opposed to those that only affect themselves
		- Privileged Instructions:
			- Can be executed only when the processor is in privileged mode
			- And trap otherwise
		- What it means
			- If what you're going to do is only going to affect you, go and do it
			- But if whatever you are doing is going to affect others, ask the OS to do it
		- x86 Sensitive and Non-Privileged Instructions
			- `CALL` - Calls the function -> Changes the PC -> But what if the PC points to code in another program -> Based on the Instruction!
			- `MOV` - moves value from a location to another -> Based on the instruction!
			- `JMP` - Jumping to PC inside code is fine -> But what if I jump to somewhere randomly in memory? -> Based on the instruction!
			- So all these depend on _arguments_ to the instruction
			- So the authors went through each instruction in x86 and listed 18 instructions that are _possibly sensitive_
			- When any of the instructions become sensitive and the application tries to execute it, do not let it do that -> because sensitive instructions are a subset of the privileged instruction -> Trap it and let OS execute it.
		- For example -> Let there be a target instruction -> Goes to Page Table -> But it can't see what is in there -> Trap triggers -> OS gets involved and verifies location -> Proceeds or throws error

- ## System Level VMs
	- ### User Mode Linux (UML)
		- Run Linux as a user-process (Guest) on top of native linux
		- Access to system hardware goes through native (host) Linux
		- Emulation
			- The host HAS TO BE LINUX
			- Guest also HAS TO BE LINUX
		- We don't have to worry about ISA, Syscall compat etc
		- The Guest Linux is actually a process for the host linux, just like there could be other processes for the host
		- How would we implement a UML?
			- The host does not know if this is a host or guest
			- The process that run on the guest, do not know that the guest is running on the host
			- So anything that the process wants to do. (say create a new thread) will pass through to the host
			- Scheduling
				- The guest will just tell the processes to stop running using signals
				- Use signals to do management
			- Memory Management
				- Allocation, swapping, free
				- Create shared MMAPs between each process so that whenever a process needs memory, so that we can MPROTECT against how much memory each process actually needs
			- TODO IOs
				- Use passthroughs
	- ### UML on x86 Rings
		- The other name for modes is rings
		- x86 has 4 rings
		- The more the rings, the more efficient it is
		- Ring 0 is most privileged, privilege decreases as it goes up
		- In User mode Linux, the guest linux itself is a process and it runs on a higher ring number when compared to host, which runs on ring 0
	- ### Para-Virtualization: Xen
		- Open Source
		- Got popular in 2000s
		- In UML, we try to keep OS as is - We could modify, but we don't
			- Here they say - Let us try not to run the default OS
			- What if the OS has a lot of sensitive information, we keep on trapping
			- We take the default OS and then we start modifying the OS - This new guest OS that we have will not be as bad as the eventual process that is to be run, will have a little more privilege than the process, but will still have lesser privileges than host OS
		- This means that the guest OS will no longer be a Stock OS
		- So the guest will do as many operations as possible until it hits a trap and has to switch over
		- VMM - Virtual Machine Monitor
			- A thin layer that takes traps and passes on things
			- It's like a passthrough or a demux machanism for traps
		- There is some application that might want to be run on a Linux, but the linux that I want to run on, is modified - This is now called Xen Linux, it has been Xen'd, it has been Xenified
		- This tries to use as few sensitive instructions as possible
		- The Xenified linux has as few drivers as possible, and they are all fake drivers that call the underlying VMM and passes through to execute the instructions
		- The implement this by creating a separate VM that has permissions to access the host/hardware. They make calls to this VM and this VM accesses the hardware.
		- Only trap when absolutely needed - somewhat more efficient
		- There are zenified versions of OSes
		- Called Paravirtualization because the guest OS is not a Stock OS, it is reengineered version of the OS
		- All it does is take traps, handle traps and passthrough
		- #### Xen on x86 Rings
			- Ring Structure
				- VMM on Ring 0
				- Xenified OS - Ring 1
				- Ring 2 - Unused
				- Ring 3 - Guest Processes
			- Precursor to UNIX was MULTIX
				- Multix required 64 rings
				- Proposed in 1960s
				- Hardware did not support 64 rings
				- Whenever you go from one ring to another, you had to trap - so complex that they could not boot even
				- So they founded UNIX
